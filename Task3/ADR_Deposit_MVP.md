# ADR-001: Концептуальная архитектура открытия депозитов онлайн (MVP)

## Статус

Предложено

## Контекст

Банк «Стандарт» планирует цифровую трансформацию депозитного направления. Текущий процесс открытия депозита полностью офлайновый: клиент приходит в отделение, ставки рассчитываются вручную в Excel, согласование занимает от 20 минут до часа с участием фронт-офиса и бэк-офиса.

**Ключевые проблемы текущей архитектуры:**
- Интернет-банк — монолит на ASP.NET MVC 4.5 / .NET Framework 4.5, интегрированный с АБС напрямую через БД Oracle.
- БД АБС перегружена; добавление онлайн-нагрузки угрожает работоспособности банка.
- Ставки по депозитам ведутся в Excel-файлах, отсутствует единый сервис управления ставками.
- Функционал СМС в ядре интернет-банка требует доработки подрядчика, что нежелательно.
- Kafka несовместим с текущей платформой интернет-банка (.NET Framework 4.5).

**Цель MVP (6 месяцев):** клиент может подать заявку на депозит в интернет-банке и на сайте. Заявки обрабатывает бэк-офис в АБС по существующему процессу.

## Use Cases

### UC-1: Просмотр доступных депозитов в интернет-банке
**Актор:** Клиент (авторизованный)
**Предусловие:** Клиент авторизован в интернет-банке.
**Основной сценарий:**
1. Клиент переходит в раздел «Депозиты».
2. Система отображает список доступных депозитов с актуальными ставками.
3. Система рассчитывает и показывает персонализированные ставки для клиента.

### UC-2: Подача заявки на депозит в интернет-банке
**Актор:** Клиент (авторизованный)
**Предусловие:** Клиент авторизован, просмотрел доступные депозиты.
**Основной сценарий:**
1. Клиент выбирает депозит, указывает счёт списания и сумму.
2. Система формирует заявку и запрашивает подтверждение СМС-кодом.
3. Клиент вводит полученный СМС-код.
4. Система подтверждает приём заявки.
5. Заявка передаётся в АБС для обработки бэк-офисом.
6. После подтверждения ставки менеджером — клиент получает СМС-уведомление.
7. После открытия депозита — клиент получает СМС-уведомление.

### UC-3: Подача заявки на депозит с сайта
**Актор:** Новый клиент (неавторизованный)
**Основной сценарий:**
1. Клиент на сайте просматривает список доступных депозитов с актуальными ставками.
2. Клиент заполняет форму заявки: ФИО и номер телефона.
3. Система принимает заявку и передаёт её в систему кол-центра.
4. Менеджер кол-центра связывается с клиентом и предлагает условия.
5. Клиенту необходимо прийти в отделение для идентификации.

### UC-4: Обработка заявки на депозит менеджером бэк-офиса (MVP)
**Актор:** Менеджер бэк-офиса депозитов
**Предусловие:** Заявка поступила из интернет-банка.
**Основной сценарий:**
1. Менеджер видит новую заявку в АБС.
2. Менеджер определяет ставку (стандартную или специальную) с учётом кредитного риска.
3. Менеджер подтверждает условия депозита в АБС.
4. Система отправляет СМС-уведомление клиенту.
5. Депозит открывается в АБС.

## Решение

### Архитектурный подход

Принято решение реализовать новый функционал в виде отдельных микросервисов на .NET 10, развёрнутых рядом с монолитом интернет-банка. Это позволяет:
- Не модифицировать ядро интернет-банка (избежать зависимости от подрядчика).
- Использовать Kafka для асинхронного взаимодействия (несовместима с .NET Framework 4.5 монолита, но совместима с .NET 10).
- Обеспечить горизонтальное масштабирование новых сервисов.
- Поэтапно переходить к микросервисной архитектуре.

### Ключевые компоненты решения

1. **Deposit Service (.NET 10)** — управление заявками на депозиты, оркестрация процесса подачи заявки, валидация данных.
2. **Rate Service (.NET 10)** — единый сервис управления ставками по депозитам, замена Excel. Доступен бэк-офису депозитов и кредитов через разграничение прав.
3. **Notification Service (.NET 10)** — отправка СМС-уведомлений через СМС-шлюз, отправка СМС-кодов подтверждения (замена доработки ядра ИБ).
4. **API Gateway** — единая точка входа для клиентских запросов из интернет-банка и сайта; маршрутизация, аутентификация, rate limiting.
5. **Kafka** — шина событий для асинхронного взаимодействия между микросервисами и интеграции с АБС.
6. **ABS Integration Service (.NET 10)** — адаптер для взаимодействия с АБС через БД Oracle (асинхронно через Kafka), изолирующий остальные сервисы от деталей АБС.

### Интеграционная модель

- **Интернет-банк (монолит) → API Gateway → Deposit Service**: HTTP REST. Монолит вызывает API Gateway для нового функционала.
- **Сайт → API Gateway → Deposit Service**: HTTP REST. Заявка с сайта передаётся через API Gateway.
- **Deposit Service → Kafka → ABS Integration Service → АБС (Oracle DB)**: Асинхронная передача заявок в АБС. Это позволяет не нагружать БД АБС синхронными запросами.
- **ABS Integration Service → Kafka → Notification Service → СМС-шлюз → Телеком**: При изменении статуса заявки в АБС — уведомление клиента по СМС.
- **Rate Service → Oracle/MS SQL**: Ставки хранятся в отдельной БД, реплицируются из АБС (базовые данные кредитного риска передаются в Rate Service).
- **Сайт → API Gateway → Deposit Service → Kafka → Система кол-центра**: Заявка с сайта маршрутизируется в кол-центр для обратного звонка.

### Диаграммы

Диаграммы C4 приложены отдельными файлами:
- **C4_Context.drawio** — диаграмма контекста системы
- **C4_Container.drawio** — диаграмма контейнеров (с детализацией интернет-банка и АБС)

## Альтернативы

### Альтернатива 1: Доработка монолита интернет-банка

Реализовать функционал депозитов внутри существующего монолита ASP.NET MVC 4.5.

**Плюсы:** Единая кодовая база, проще деплой.
**Минусы:**
- Зависимость от подрядчика при обновлении ядра.
- Невозможность использовать Kafka (.NET Framework 4.5 несовместим).
- Сложность горизонтального масштабирования монолита.
- Увеличение технического долга.

**Причина отклонения:** Противоречит требованиям масштабируемости, независимости от подрядчика и использования Kafka.

### Альтернатива 2: Прямая интеграция новых сервисов с АБС через API

Создать REST API поверх АБС и вызывать его синхронно из новых сервисов.

**Плюсы:** Простота реализации, актуальные данные в реальном времени.
**Минусы:**
- БД АБС уже перегружена; синхронные вызовы увеличат нагрузку.
- АБС не имеет готового REST API — создание потребует значительных доработок.
- Нарушает требование «избегать прямой работы интернет-банка с API АБС».
- АБС масштабируется только вертикально.

**Причина отклонения:** Риск дестабилизации основной банковской системы.

### Альтернатива 3: Использование RabbitMQ вместо Kafka

**Плюсы:** Проще в настройке, подходит для текущих объёмов.
**Минусы:**
- Бизнес явно указал на Kafka «на перспективу».
- Меньше возможностей для обработки потоков событий.
- Двойная миграция в будущем.

**Причина отклонения:** Прямое указание бизнеса на Kafka.

## Последствия и ограничения

### Положительные
- Независимость от подрядчика: новый функционал разрабатывается командой банка на .NET 10.
- Горизонтальное масштабирование новых микросервисов.
- Изоляция от перегруженной БД АБС через асинхронную интеграцию.
- Единый сервис ставок заменяет ручной Excel-процесс.
- Поэтапная модернизация интернет-банка без «большого взрыва».

### Ограничения
- На этапе MVP заявки обрабатываются асинхронно — клиент не получает мгновенного результата.
- Требуется развёртывание Kafka-кластера — инфраструктурные затраты.
- ABS Integration Service зависит от структуры БД АБС Oracle — при изменениях в АБС потребуется адаптация.
- Асинхронная модель интеграции приводит к eventual consistency — данные в новых сервисах могут отставать от АБС.
- Необходимо обеспечить идемпотентность обработки сообщений Kafka.

### Риски
- Команда банка может не иметь достаточного опыта с Kafka — требуется обучение.
- Миграция со старого процесса (Excel → Rate Service) требует тщательной верификации расчётов.
- Интеграция монолита ИБ с API Gateway требует минимальных доработок на стороне монолита.
