# ADR-003: Подача заявки на кредит онлайн (интернет-банк и сайт)

## Статус

Предложено

## Контекст

Банк «Стандарт» планирует реализовать подачу заявки на кредит онлайн — из интернет-банка и с сайта. Реализация запланирована на горизонте одного года после MVP по депозитам.

**Текущий кредитный процесс:**
- Клиент подаёт заявку только в отделении → менеджер оформляет в АБС.
- Заявки из АБС попадают в Кредитный конвейер раз в сутки через интеграцию по БД.
- Менеджеры кредитного отдела обрабатывают заявки в Кредитном конвейере, вызывая систему скоринга.
- Скоринг использует данные АБС (раз в сутки), Кредитного конвейера (раз в сутки) и БКИ (онлайн).
- Одобренные заявки возвращаются в АБС раз в сутки.

**Ключевые проблемы:**
1. АБС → Кредитный конвейер: обмен раз в сутки через БД, ускорить невозможно.
2. Предодобренные заявки должны обрабатываться в тот же рабочий день — текущая batch-интеграция не позволяет этого.
3. Система скоринга перегружена в рабочие часы — нельзя нагружать её предрасчётами.
4. Новый клиент с сайта: для предварительного решения доступны только данные БКИ.
5. Заявка, начатая на сайте, должна продолжаться в отделении при визите клиента.

**Архитектурная база:** решение строится поверх микросервисной платформы, созданной в рамках MVP депозитов (ADR-001): API Gateway, Kafka, Notification Service.

## Use Cases

### UC-1: Просмотр кредитных предложений на сайте
**Актор:** Новый клиент (неавторизованный)
**Основной сценарий:**
1. Клиент открывает раздел «Кредиты» на сайте.
2. Система отображает список доступных кредитных продуктов с условиями.
3. Условия загружаются из Кредитного конвейера, где хранится полная информация о кредитных продуктах.

### UC-2: Подача заявки на кредит с сайта (без паспортных данных)
**Актор:** Новый клиент
**Основной сценарий:**
1. Клиент заполняет форму: ФИО и номер телефона.
2. Система принимает заявку.
3. Клиент получает СМС о необходимости визита в отделение для идентификации и оформления.

### UC-3: Подача заявки на кредит с сайта (с паспортными данными)
**Актор:** Новый клиент
**Основной сценарий:**
1. Клиент заполняет форму: ФИО, телефон и паспортные данные.
2. Система выполняет запрос в систему скоринга, используя данные БКИ.
3. Клиент получает предварительное решение (одобрение / отказ).
4. Клиент получает СМС о необходимости визита в отделение.
5. Заявка сохраняется для продолжения обработки в отделении.

### UC-4: Просмотр кредитных предложений в интернет-банке
**Актор:** Клиент (авторизованный)
**Основной сценарий:**
1. Клиент открывает раздел «Кредиты» в интернет-банке.
2. Система отображает список доступных кредитов с актуальными условиями.
3. Если для клиента есть предодобренное предложение — оно отображается отдельно с рассчитанной суммой и ставкой.

### UC-5: Подача заявки на кредит в интернет-банке (обычная)
**Актор:** Клиент (авторизованный)
**Основной сценарий:**
1. Клиент выбирает кредитный продукт, указывает счёт зачисления и данные заявки.
2. Система запрашивает подтверждение СМС-кодом.
3. Клиент подтверждает операцию.
4. Заявка передаётся в Кредитный конвейер для обработки.
5. Клиент получает СМС о приёме заявки.
6. При изменении статуса — СМС-уведомление.

### UC-6: Подача заявки по предодобренному предложению в интернет-банке
**Актор:** Клиент (авторизованный)
**Предусловие:** Клиенту отображается предодобренное предложение.
**Основной сценарий:**
1. Клиент нажимает «Подать заявку» на предодобренном предложении.
2. Система заполняет данные автоматически, клиент указывает счёт зачисления.
3. Подтверждение СМС-кодом.
4. Заявка передаётся напрямую в Кредитный конвейер (минуя batch-интеграцию с АБС).
5. Повторный скоринг выполняется по упрощённой процедуре (данные уже есть).
6. Заявка обрабатывается менеджерами в течение того же рабочего дня.
7. Клиент получает СМС об одобрении/отказе.

### UC-7: Продолжение обработки онлайн-заявки в отделении
**Актор:** Менеджер фронт-офиса
**Предусловие:** Клиент подал заявку с сайта и пришёл в отделение.
**Основной сценарий:**
1. Менеджер находит заявку клиента в АБС по номеру телефона/данным.
2. Менеджер продолжает работу с существующей заявкой (не создаёт новую).
3. Менеджер проводит идентификацию и дополняет заявку недостающими данными.

### UC-8: Расчёт предодобренных предложений (фоновый процесс)
**Актор:** Система (автоматический процесс)
**Триггер:** Нерабочие часы (ночь).
**Основной сценарий:**
1. Система выбирает клиентов, для которых нужен расчёт предодобренных предложений.
2. Для каждого клиента запрашивается скоринг в системе кредитного скоринга.
3. На основании результата рассчитывается приемлемая сумма и ставка.
4. Предодобренное предложение сохраняется и становится доступно клиенту в интернет-банке.

## Решение

### Архитектурный подход

Решение расширяет микросервисную платформу MVP (ADR-001) новыми компонентами для кредитного процесса. Ключевое архитектурное решение — прямая интеграция нового Credit Application Service с Кредитным конвейером через REST API, минуя медленную batch-интеграцию через БД АБС.

### Новые компоненты

1. **Credit Application Service (.NET 10)** — приём и управление кредитными заявками из интернет-банка и сайта. Хранение заявок в собственной БД. Оркестрация процесса подачи заявки.

2. **Pre-Approved Offer Service (.NET 10)** — фоновый расчёт предодобренных предложений. Запускается в нерабочие часы, запрашивает скоринг для клиентов и сохраняет результаты.

3. **Credit Conveyor API Adapter (.NET 10)** — адаптер для прямой отправки заявок в Кредитный конвейер через REST API Camunda, минуя batch-канал через АБС.

### Модифицируемые компоненты

1. **Кредитный конвейер** — добавление REST API для приёма заявок извне (если не реализовано). Camunda BPM поддерживает REST API из коробки.

2. **Система кредитного скоринга** — без изменений. Используется существующий REST API (Flask). Фоновые расчёты выносятся на нерабочие часы.

3. **Notification Service (.NET 10, из MVP)** — добавление обработки событий статусов кредитных заявок для отправки СМС.

4. **API Gateway (из MVP)** — добавление маршрутов для кредитных API.

5. **ABS Integration Service (из MVP)** — синхронизация кредитных заявок с АБС для обеспечения единого представления заявки (чтобы менеджер в отделении мог продолжить работу).

### Интеграционная модель

```
Сайт / Интернет-банк
    │
    └──[HTTPS]──→ API Gateway
                      │
                      ├──→ Credit Application Service (.NET 10)
                      │        │
                      │        ├──[REST API]──→ Система скоринга (Flask)
                      │        │                    └──→ БКИ [REST API]
                      │        │
                      │        ├──[REST API]──→ Credit Conveyor API Adapter
                      │        │                    └──→ Кредитный конвейер (Camunda REST API)
                      │        │
                      │        ├──[Kafka]──→ ABS Integration Service → АБС (Oracle)
                      │        │              (синхронизация заявок для отделений)
                      │        │
                      │        └──[Kafka]──→ Notification Service → СМС-шлюз
                      │
                      └──→ Pre-Approved Offer Service (.NET 10)
                               │
                               ├──[REST API]──→ Система скоринга (ночью)
                               │
                               └──[SQL]──→ Credit DB (MS SQL)
```

### Потоки данных для предодобренных предложений

1. **Ночной расчёт:** Pre-Approved Offer Service выбирает клиентов → запрашивает скоринг → сохраняет предложения в Credit DB.
2. **Отображение:** Клиент логинится в ИБ → API Gateway → Credit Application Service → читает предложения из Credit DB.
3. **Подача заявки:** Клиент подаёт заявку → Credit Application Service → Credit Conveyor API Adapter → Кредитный конвейер (прямая отправка через REST API Camunda, минуя batch).
4. **Обработка:** Менеджер в Кредитном конвейере обрабатывает заявку → повторный упрощённый скоринг → решение → событие в Kafka → СМС клиенту.

### Обеспечение непрерывности заявки (сайт → отделение)

1. Заявка с сайта сохраняется в Credit DB (Credit Application Service).
2. Через ABS Integration Service заявка синхронизируется в АБС.
3. При визите клиента в отделение менеджер находит заявку в АБС и продолжает с ней работу.
4. Обновления из АБС возвращаются через ABS Integration Service в Credit Application Service.

### Диаграммы

Диаграммы C4 приложены отдельными файлами:
- **C4_Context_Credit.drawio** — диаграмма контекста
- **C4_Container_Credit.drawio** — диаграмма контейнеров

## Альтернативы

### Альтернатива 1: Подача заявок через АБС (существующий batch-канал)

Все заявки из онлайн-каналов передаются в АБС, а оттуда раз в сутки — в Кредитный конвейер.

**Плюсы:**
- Не требует доработки Кредитного конвейера.
- Использование существующей проверенной интеграции.

**Минусы:**
- Обработка заявок занимает минимум сутки (batch раз в день).
- Невозможно выполнить требование обработки предодобренных заявок в тот же день.
- Увеличивает нагрузку на БД АБС.

**Причина отклонения:** Не удовлетворяет бизнес-требованию обработки заявок в тот же день.

### Альтернатива 2: Замена Кредитного конвейера на новую систему

Создать новую систему обработки кредитных заявок, которая интегрирована с онлайн-каналами.

**Плюсы:**
- Полный контроль над архитектурой.
- Нативная поддержка онлайн-заявок.

**Минусы:**
- Огромные затраты на разработку и миграцию.
- Существующий Кредитный конвейер уже проверен и используется бизнесом.
- Дублирование функционала.
- Потеря накопленной бизнес-логики обработки заявок.

**Причина отклонения:** Непропорциональные затраты; существующий конвейер расширяем.

### Альтернатива 3: Предрасчёт скоринга в рабочие часы

Запускать расчёт предодобренных предложений непрерывно, в том числе днём.

**Плюсы:**
- Более актуальные предложения.

**Минусы:**
- Система скоринга испытывает повышенную нагрузку в рабочие часы.
- Дополнительная нагрузка может привести к деградации основного процесса обработки заявок.
- Прямое нарушение требования не нагружать скоринг дополнительными процессами днём.

**Причина отклонения:** Явное ограничение бизнеса.

### Альтернатива 4: Единый Credit Service без отдельного Pre-Approved Offer Service

Объединить логику заявок и предодобренных предложений в одном сервисе.

**Плюсы:**
- Меньше сервисов, проще deployment.

**Минусы:**
- Разная природа нагрузки: синхронная (заявки) vs. тяжёлая batch (ночной скоринг).
- Ночной batch-процесс может повлиять на доступность API.
- Нарушает Single Responsibility Principle.

**Причина отклонения:** Различные паттерны нагрузки требуют разделения.

## Ограничения решения

1. **Batch-интеграция АБС ↔ Кредитный конвейер сохраняется.** Прямой канал через REST API Camunda используется параллельно, но не заменяет batch. Исторические заявки из отделений продолжают идти через batch.

2. **Eventual consistency.** Заявка, поданная онлайн, появляется в АБС с задержкой (асинхронная синхронизация через Kafka). Менеджер в отделении может не сразу увидеть заявку — требуется учёт задержки в SLA.

3. **Зависимость от внешних систем.** Предварительное решение на сайте зависит от доступности системы скоринга и БКИ. При их недоступности — degradation: заявка принимается без предварительного решения.

4. **Ночной расчёт предложений ограничен окном.** Количество клиентов, для которых можно рассчитать предложения за ночь, ограничено пропускной способностью скоринга. При росте клиентской базы потребуется оптимизация.

5. **Кредитный конвейер — коробочное решение.** Добавление REST API для приёма заявок извне может потребовать участия подрядчика, если стандартный API Camunda недостаточен. Однако в IT-отделе есть специалисты, способные менять обработчики и описания бизнес-процессов.

6. **Паспортные данные с сайта** требуют повышенных мер защиты (шифрование, ограниченное хранение, соответствие 152-ФЗ).

7. **Предодобренные предложения могут устареть.** Между расчётом (ночью) и подачей заявки (днём) финансовая ситуация клиента может измениться. Поэтому при подаче заявки выполняется повторный упрощённый скоринг.
